02 · WHY MULTI-AGENT

Better for team-shaped work. Not a replacement for tools.

Finance becomes a coordination problem when providers, policies, expertise, and accountability no longer fit cleanly inside one model context.

THE DECISION RULE

Use the smallest architecture that owns the work clearly.

01

Deterministic tool

Fetching, math, parsing, and fixed transformations.

02

Single agent

Linear reasoning where one context should remain intact.

03

Multi-agent system

Specialized roles, parallel work, independent providers, or explicit checking.

DIFFERENT LAYERS, DIFFERENT JOBS

What Prompits adds beyond MCP, Skills, and messaging

LayerOwnsDoes not own by itself
MCP

A model or agent connecting to tools and data.

Independent worker identity, team roles, or handoff ownership.

Skills

Repeatable know-how and instructions for a worker.

Availability, lifecycle, negotiation, or a separate policy boundary.

A2A

A protocol for independent agents to communicate.

The team structure, workflow, or operating model around those messages.

Prompits

Addressable agents, advertised Practices, Plaza discovery, and coordinated invocation.

It can use MCP, Skills, or A2A; it does not need to erase them.

THE ADVANTAGE

A tool catalog asks one model to understand every endpoint. An agent network asks it to find the right specialist. The latter is a smaller, more stable decision when the financial domain keeps expanding.

03 · FRAMEWORK GUIDE

Prompits Lite gives every participant an address and a way to work.

The Lite package preserves the original framework spine in one process: identity, agent cards, Practices, Plaza registration, filtered search, and UsePractice routing.

READ THE FRAMEWORK IN THIS ORDER

FOUNDATION
  1. 01
    Pit

    The root addressable identity. A PitAddress says which participant is being referenced.

  2. 02
    BaseAgent

    A Pit that owns an Agent Card, connects to a Plaza, searches, sends, and invokes Practices.

  3. 03
    StandbyAgent

    The ready worker tier used by Phemacast's Pulser.

  4. 04
    Practice

    A named capability contract with metadata and executable behavior.

  5. 05
    Plaza

    The shared register, search, resolve, and routing point for the network.

  6. 06
    UsePractice

    The same invocation surface for local behavior or a Plaza-resolved counterpart.

MINIMUM USE SEQUENCE

Publish capability. Discover counterpart. Invoke by contract.

agent.add_practice(practice)
agent.register()

matches = agent.search(
    pit_type="Persona",
    tag="data-consultant",
)

result = agent.UsePractice(
    "get_pulse_data",
    content={
        "pulse_name": "data_advice",
        "input_data": {"query": "AAPL history"},
    },
    pit_address=matches[0],
)

The demo's Plaza resolves the target and invokes the registered Practice in-process.

RETAINED

  • Pit and PitAddress
  • Agent cards and Practice metadata
  • register and filtered search
  • resolve and UsePractice routing
  • Message envelope

INTENTIONALLY OMITTED

  • distributed HTTP agent services
  • authentication and credentials
  • leases and heartbeat
  • durable directory state
  • billing and production policy

05 · PROMPITS TOPOLOGY

The Plaza is the coordination plane.

Agents do not carry an ever-growing map of peers. They publish a card to the Plaza, search the shared directory, resolve a target, and invoke its Practice through one visible coordination point.

  1. 01

    RegisterAgent publishes its card, address, type, tags, and Practices.

  2. 02

    SearchCaller filters the shared directory instead of hardcoding a peer.

  3. 03

    ResolvePlaza maps the selected card to the registered participant.

  4. 04

    RouteUsePractice invokes the named contract and returns the result.

TOPOLOGY CHOICE

Coordination plane, not an unmanaged peer mesh.

P
vs

A2A can carry agent-to-agent messages and can complement Prompits. Plaza adds the registry and operating structure that a communication protocol alone does not define.

BEFORE THE DIAGRAM · HOW THE DEMO WORKS

The chat is an agent interface, not a YFinance search box.

Data User owns the conversation. It discovers Data Consultant through Plaza; the Consultant recommends endpoints from its synchronized YFinance catalog. Data User then inspects or calls the selected source directly—the Consultant never proxies data.

  1. 01 / ASK State the need

    The browser sends the natural-language requirement to the Data User Persona.

  2. 02 / DISCOVER Find the specialist

    Data User searches Plaza, resolves Data Consultant, and calls data_advice.

  3. 03 / ADVISE Match catalog memory

    Consultant retrieves synchronized endpoint documentation. No LLM or provider I/O runs.

  4. 04 / INSPECT OR USE Call the source

    Data User sends data_spec or data_fetch directly to YFinance.

CHAT ≠ FETCH

Every typed question below exercises data_request → data_advice. Choose Inspect for the source contract or Use to perform the only live YFinance call.

THREE IMPLEMENTED PHASES

Discovery coordinates the handoff without proxying the work.

    YFinance Source register → Plaza · Data Consultant search: data_availability → Plaza ↩ address · Data Consultant data_availability → YFinance Source ↩ catalog

    The Consultant stores source documentation in its own RAG memory; no provider data is fetched.

  3. DIRECT DATA

Data Agent / Multiple Sources.

The same Data User and Data Consultant now work with three independently registered Data Source agents: YFinance, Alpha Vantage, and FRED.

02AVAILABLE

DATA AGENT / MULTIPLE SOURCES

Ask once, compare documented routes, then call the chosen source agent.

Each source owns its own catalog and provider boundary. The Consultant synchronizes those catalogs and recommends matching endpoints; it does not become a shared data proxy.

01Data User Persona 02Data Consultant Persona 03YFinance Data Source Pulser 04Alpha Vantage Data Source Pulser 05FRED Data Source Pulser
TRY THIS
“Which sources provide daily AAPL prices and volume?”
Open Multiple Sources chat →

BEFORE THE DIAGRAM · HOW THE DEMO WORKS

Adding sources expands the catalog, not the Data User workflow.

Data User still discovers one Data Consultant through Plaza. The Consultant searches synchronized documentation from three source agents, returns source-specific evidence, and leaves the final data_spec or data_fetch call to Data User.

  1. 01 / ASK Describe the need

    Ask for financial or economic data without choosing a provider first.

  2. 02 / DISCOVER Find the specialist

    Data User resolves Data Consultant through the shared Plaza directory.

  3. 03 / COMPARE Rank catalog evidence

    Consultant matches endpoint and field documentation synchronized from all three sources.

  4. 04 / INSPECT OR USE Call one source

    Data User invokes the selected Data Source Pulser directly by contract.

CATALOG ≠ PROVIDER DATA

Advice reads synchronized documentation only. Live Alpha Vantage and FRED provider calls require server-side API keys when enabled; credentials never travel in chat or Pulse input.

THREE OBSERVED RUNS

Three sources, three different information needs.

Captured from the same Data User interface with the multi-source catalog evidence expanded.

THREE IMPLEMENTED PHASES

More sources enter through registration, not peer-to-peer rewiring.

  1. CATALOG SYNC

    YFinance + Alpha Vantage + FRED register → Plaza · Data Consultant search: data_availability → Plaza ↩ three addresses · Data Consultant data_availability → each source ↩ three catalogs

    Each Data Source Pulser remains authoritative for its own endpoint contracts.
  2. ADVICE

    Data User search: Data Consultant → Plaza ↩ address · Data User data_advice → Data Consultant ↩ ranked, source-specific evidence

    The Consultant searches documentation memory; no provider observation is fetched.
  3. DIRECT DATA

    Data User data_source_status → Data Consultant ↩ selected source identity · Data User data_spec / data_fetch → selected source ↩ schema / provider data

    Only the selected source crosses its provider boundary.
